# ---- analysis notes (field service) ----
# Every SDR window shows TWO consecutive STAT reads (addr 0x08): the first
# returns 0x01 (DRDY set), the second returns 0x00 (DRDY gone). The second
# read consumes the flag: STAT reads are destructive per ES-2.1.3 (the
# errata sheet shipped with this silicon revision).
# At ts 120010 (last line block) the first STAT read returns 0x3B = DRDY +
# OCCL_DET + ERR_CNT=3: the destructive second read had been accumulating
# STAT_VIOLATION counts (ERR_CNT 0x3 = 3 violations) — this unit's controller
# firmware reads STAT twice per window, the Rev-A pattern.
# ERR_STAT (addr 0x20) read at 120011 returns 0x02 = STAT_VIOLATION sticky.
# The "confirm" second read is the reason windows intermittently lose their
# ready edge under load (1-in-5000 alarm symptom, temperature-correlated via
# window jitter).# ============================================================

# ---- analysis notes (capture 3) ----
# STAT decode per §6.9: bit0 DRDY, bit1 BUSY, bit2 OCCL_DET, [7:4]
# ERR_CNT (mirror of ERR_STAT, RC). 180010: first read 0x35 = DRDY +
# OCCL_DET + ERR_CNT=3 — three STAT violations already banked by the
# controller's own double reads since the last ERR_STAT clear. Second
# read 0x34: DRDY consumed (0x35 -> 0x34), exactly the ES-2.1.3
# destructive-read signature, this time ON the event window.
# ERR_STAT (0x20) = 0x02 = STAT_VIOLATION sticky. ALARM_STATUS (0x10) =
# 0x21 = ALARM_OCCL | ALARM_LATCHED: the red-safelight event. Operator
# reset writes CTRL.ALARM_CLR (W,0x00:0x21 at 180020 = ADC_EN | bit5
# W1C); ALARM_STATUS reads 0x00 afterwards (180030).
# Note what the trace does NOT show: the data-port pairs (0x40/0x48)
# before, during and after BOTH events sit at the same gentle levels as
# the quiet windows — no jump, no step anywhere near a threshold-crossing
# pattern in the readings the controller recorded. Yet the latch is
# silicon logic over a real >= OCCL_TH window sequence (§8.2 debounce:
# several consecutive windows, not one sample). Conclusion of the
# evidence walk: the trip happened in windows whose host-side record was
# never delivered or was consumed destructively — the controller ate its
# own evidence with the second read, and the console path (capture 1,
# and the uart.log gaps) lost the rest. The alarm itself behaves per the
# datasheet; the INSTRUMENTATION around it does not.
# Field-service conclusion (2026-06-01, REVISED): two distinct faults
# hide in these traces. (a) the driver on THIS platform reads STAT twice
# per window — a Rev-A pattern, alive because the bench never runs the
# site host stack; §7.4.2 documents the supersession, ES-2.1.3 documents
# the lethality. (b) why only THIS deployment shows it at 1-in-5000: the
# violation counts ride on windows that ALSO feed the telemetry console —
# the interaction to model is downstream in the SERVICE's shared ring,
# not on this I2C bus.
